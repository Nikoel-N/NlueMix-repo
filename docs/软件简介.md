# NlueMix 软件简介

> 一台电脑，多个人的声音，一个蓝牙音响。

---

## 一句话说清

蓝牙音响**只能同时连一台设备**——这是音响芯片决定的，换什么软件都改不了。

NlueMix 的办法是：**让电脑当中间人**。

```
   手机 1 ──Wi-Fi──┐
   手机 2 ──Wi-Fi──┼──▶  电脑（混音 + 自动让路）  ──蓝牙──▶  音响
   手机 3 ──Wi-Fi──┘
   电脑自己的声音 ──┘
```

音响那边**始终只有一条蓝牙连接**，但你能同时听到最多 3 台手机 + 电脑的声音。

**对使用者的感受来说：几个人都能把声音放到同一个音响上。**

---

## 它解决什么问题

你是不是遇到过这些情况：

- **打游戏死了等复活**，想躺沙发上用手机放首歌，但音响连着电脑，还得手动去关电脑声音
- **程序/模型在跑，等结果的时候**想刷会儿视频，声音却只能从手机小喇叭出来
- **朋友来家里**，想轮流放歌，但音响一次只能连一个人
- 电脑手机**来回切歌**，每次都要重新配对，烦

NlueMix 就是干这个的。

## 核心功能

### 自动让路（这是灵魂功能）

手机一出声，**电脑自动静音**；手机停下来，**电脑声音自动回来**。全程不用你点任何东西。

| 模式 | 效果 |
|---|---|
| **自动让路**（默认） | 手机出声 → 电脑淡出静音；手机停 2 秒 → 电脑淡入恢复 |
| 自动压低 | 手机出声 → 电脑音量降到 20%（两个都听得见） |
| 一起放 | 不分主次，混着播 |
| 手动 | 只用按钮切换 |

**技术实现**：实时算手机音频的音量和峰值，用**双阈值迟滞**判断（判定「有声」和判定「无声」的门槛不一样），避免在临界点上反复横跳。
- 连续 **320 ms** 有声 → 开始让路
- 连续 **1800 ms** 无声 → 恢复
- 淡入淡出 **0.1–0.3 秒**，听感上不会「啪」一声

### 三路独立音源

最多接 3 台手机，**每路独立音量、独立静音**，界面上就是一张卡片一根滑杆。

### 音质不打折

| 路段 | 处理方式 |
|---|---|
| 手机 → 电脑 | **48 kHz 立体声 PCM 无损直传**（局域网带宽不是瓶颈） |
| 电脑内部 | float32 混音 + 软限幅保护（防削顶爆音） |
| 电脑 → 音响 | 交给 Windows 蓝牙栈，音质损失**只有这一次编码** |

**关键点：软件不额外引入任何一次编解码。** 你平时蓝牙听歌是什么音质，经过 NlueMix 还是什么音质（手机那段是无损的）。

### 轻、干净、免安装

- 绿色免安装，双击就能跑
- 内存 ~130 MB，CPU 待机接近 0
- **不装虚拟声卡、不改系统设置**，卸载了不留痕
- **无广告、无推广、无遥测、无账号**
- 除了局域网内和手机通信，**不连接任何外部服务器**

## 系统要求

| 端 | 要求 |
|---|---|
| **电脑** | Windows 10 版本 2004（内部版本 19041）或更高 / Windows 11；蓝牙 4.0+ 适配器 |
| **手机** | **Android 10 或更高**（系统音频采集是 Android 10 才有的 API） |
| **网络** | 手机和电脑在**同一个局域网**下（手机 Wi-Fi，电脑可有线可无线） |

---

## 已知限制（说在明处）

| 限制 | 原因 |
|---|---|
| **蓝牙音质由硬件决定** | Windows 允许选编码器（SBC/AAC），取决于网卡和音响。软件改不了 |
| **延迟约 200–400 ms** | 蓝牙本身的延迟。**不适合打游戏、不适合当 KTV 麦克风** |
| **首次配对必须走系统设置** | Windows 没开放「程序内发起配对」的 API |
| **iOS 完全不支持** | 苹果不开放系统音频采集 |
| **未声明允许被采集的应用抓不到** | 见下方「采集能力说明」，这是 Android 的平台规则 |
| **手机录音时状态栏有系统图标** | 安卓的强制提示，去不掉 |

### 采集能力说明（实测结论）

Android 从 10 开始提供系统音频采集，但有一条硬规则：
**只有在自己清单里声明了 android:allowAudioPlaybackCapture="true" 的应用，它的声音才能被采集；默认是 false。**

同一个手机、同一套采集代码的受控实验（详见《B站采集问题-结论报告.md》）：

| 音源 | 应用是否声明允许采集 | 实测采集峰值 |
|---|---|---|
| 测试音（1 kHz 正弦） | 声明了 | **13106**（理论 13107，误差 1 个 LSB） |
| 同一个测试音 | 未声明 | **0** |
| B 站实际播放 | 未声明 | **0** |

**所以能采到什么，取决于对方应用是否放行，不取决于本软件。**

两条采集通路：

| 通路 | 用户门槛 | 能采的范围 |
|---|---|---|
| App 通路（MediaProjection） | 点一次「允许录屏」 | 仅声明了允许采集的应用 |
| shell 通路（adb） | 一次性开启无线调试 | 全部应用 |

## 安全说明

**设计上是安全的**：蓝牙配对走系统、不联网外传、代码完全开源、只会播放音频。

**已实现的三道防线**：

| 防线 | 机制 |
|---|---|
| **握手限流** | 同一 IP 错 5 次锁 60 秒；锁定期内正确的连接码也进不来 |
| **UDP 源校验** | 音频包必须来自跟握手同一个 IP，堵掉抢注漏洞 |
| **包严格校验** | 多重检查，畸形包在碰音频线程之前就被丢掉 |

**还没做的（如实告知）**：

| 项 | 说明 |
|---|---|
| 传输未加密 | 同一局域网下抓包的人能还原音频内容 |
| 连接码是静态的 | 不会自动轮换（可加） |

**威胁模型**：攻击者需要**和你连同一个局域网**。
- 大多数咖啡馆/学校/酒店的公共 Wi-Fi 有**客户端隔离** → 安全
- 宿舍、合租房、公司内网、手机热点**通常不隔离** → 存在风险

**攻击者拿不到**：你的文件、密码、系统控制权。
**最坏情况**：别人能往你音响里放声音，或听到你在放什么。

> **结论**：**自己家局域网用，当前版本足够安全。**

## 技术架构

```
电脑端（.NET 8 + WPF）
├── Audio/       WASAPI 输出 → 混音 → 软限幅 → 蓝牙音箱
├── Bluetooth/   从 Windows 配对数据库识别音响
├── Network/     TCP 握手 + UDP 收流（可回落 TCP）
├── Core/        环形缓冲、静音检测、增益平滑、DSP
└── UI/          深色界面

手机端（Kotlin + 原生 Android）
├── MainActivity.kt      两个输入框 + 一个按钮
├── CaptureService.kt    MediaProjection + AudioPlaybackCapture
└── Protocol.kt          TCP 握手 + UDP 音频（与电脑端严格一致）

shell 采集端（Java + adb，可选通路）
└── CaptureServer.java   app_process + REMOTE_SUBMIX，可采全部应用
```

**通信协议**：控制走 TCP 47820（可靠），音频默认走 UDP 47821（低延迟），可切换 TCP。
**为什么音频优先 UDP**：TCP 丢包会重传，重传会让后面的数据排队等着（队头阻塞），结果是「卡一下 + 延迟越积越多」。音频**宁可丢 20 ms，也不要整体延迟**。
