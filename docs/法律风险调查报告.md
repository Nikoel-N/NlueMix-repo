# NlueMix 法律风险调查报告

日期：2026-10-12

> **免责说明：本文是基于公开法律法规和应用商店政策的整理，不是法律意见。
> 如果计划商业分发，发布前请找执业律师审阅。**

---

## 一、最要紧的一条：概括性免责无效

### 《中华人民共和国民法典》第五百零六条

> 合同中的下列免责条款无效：
> （一）造成对方**人身损害**的；
> （二）因**故意或者重大过失**造成对方财产损失的。

### 《中华人民共和国消费者权益保护法》第二十六条

> 经营者在经营活动中使用格式条款的，应当以显著方式提请消费者注意商品或者服务的数量和质量、
> 价款或者费用、履行期限和方式、**安全注意事项和风险警示**、售后服务、民事责任等与消费者有重大利害关系的内容，
> 并按照消费者的要求予以说明。
>
> 经营者不得以格式条款、通知、声明、店堂告示等方式，作出**排除或者限制消费者权利、减轻或者免除经营者责任、
> 加重消费者责任**等对消费者不公平、不合理的规定……
>
> 格式条款、通知、声明、店堂告示等含有前款所列内容的，**其内容无效**。

### 这意味着什么

| 想写的话 | 是否有效 | 说明 |
|---|---|---|
| 「确认后我们不负责」 | **无效** | 概括免责，落进 506 条 |
| 「造成人身损害我们不负责」 | **无效** | 506 条第一项直接禁止 |
| 「我们故意或重大过失造成的损失不负责」 | **无效** | 506 条第二项直接禁止 |
| 「局域网传输未加密，同一网络下他人可能还原你播放的音频」 | **有效** | 具体风险告知，属 26 条要求的"风险警示" |
| 「本软件不收集、不上传任何数据」 | **有效** | 事实陈述 |
| 「采集需系统授权，未授权的应用采不到声音」 | **有效** | 功能边界说明 |

**所以设计上必须换一种写法**：不是"我不负责"，而是"**具体会发生什么、你需要知道什么**"。

### 写"不负责"反而更危险

如果发生纠纷，"已确认免责"这句话**不能免除责任**，
但法院可能据此认定**开发者明知风险仍放任**，在过错认定上对开发者更不利。

## 二、无障碍权限：如果做自动化，这是最大的合规风险

### Google Play 无障碍 API 政策（原文摘录）

> Accessibility API 不能用于：
> - 在未经用户许可的情况下**更改用户设置**，或者阻碍用户停用或卸载任何应用或服务……
> - **规避 Android 内置的平台安全控制机制、隐私控制机制和通知**；或
> - 以具有欺骗性或其他违反 Google Play 开发者政策的方式更改或利用界面。
>
> Accessibility API 并非为实现下列用途而设计，应用也不得请求使用该 API 来实现这些用途：
> - 远程通话录音
> - **能够自主发起、规划和执行操作或决策的应用**

### 对号入座

| 我们计划做的事 | 对应哪条禁区 |
|---|---|
| 自动点开「无线调试」开关 | 更改用户设置 / 规避平台安全控制 |
| 自动读取配对码并完成配对 | 自主发起、规划和执行操作 |
| 自动读取端口 | 自主规划执行 |

**结论：这一功能不能上 Google Play。** 中国应用商店同样把无障碍列为重点审查敏感权限，
上架风险很高。

**可行的边界**：
- 只走自主分发（官网 / GitHub Releases）
- 在应用内做**显著披露**并取得**明确同意**（Google 政策对非无障碍工具的要求）
- 用户**可随时关闭**该功能，关闭后软件核心功能仍可用（只是要手动配置）
- 绝不把它标记为 `isAccessibilityTool=true`

### 如果只做"半自动"（推荐）

还有一个低风险替代：**无障碍只负责跳转页面，读取和输入仍由用户完成**。
这样仍属于"更改用户设置"的灰区，但自动化程度降低，审核风险小很多。

## 三、个人信息保护法（PIPL）

| 条款 | 要求 | 我们的对应 |
|---|---|---|
| 第 6 条 | 最小必要 | 只采集音频，不采集屏幕内容、不读通讯录 |
| 第 13 条 | 取得个人同意 | 开屏弹窗 + 系统权限弹窗 |
| 第 17 条 | 告知处理目的、方式、种类、保存期限 | **弹窗里逐条写明** |
| 第 28 条 | 敏感个人信息需**单独同意** | 无障碍权限必须单独一个确认，不能混在一起 |
| 第 15 条 | 有权撤回同意 | **必须提供撤回入口**（设置里能关） |

**关键**：PIPL 第 15 条给了用户撤回同意的权利。
所以「永久关闭弹窗」这个设计**必须配一个"重新开启/撤回同意"的入口**，
否则就是"排除消费者权利"，落进消保法 26 条。

## 四、网络安全法 / 数据安全法

- 未加密传输：同网段可嗅探 → **必须在弹窗里如实告知**
- 我们不联网外传、不收集数据 → 不构成数据处理者，PIPL 义务大幅减轻
- 但如果将来加云端功能，性质会变

## 六、杀毒软件误报

「无障碍 + 提权 + 局域网传输」是典型恶意软件特征组合。
参考：安全厂商披露过 **RedHook 恶意软件利用 Wireless ADB 获取 shell 权限**。

对策：
- 开源可审计
- 提供文件哈希
- 准备误报申诉材料
- **在弹窗里主动说明"可能被杀毒软件误报以及为什么"** —— 这反而能建立信任

## 八、结论与建议

### 弹窗设计上

1. **删掉「确认后我们不负责」**，换成逐条具体的风险告知
2. 权限、已知问题、安全风险**分三块全部写明**，统一字号，不放小字
3. 保留「永久关闭」选项，但**必须同时提供"重新开启"入口**（PIPL 第 15 条撤回权）
4. 无障碍权限（如果做）**单独一个确认**，不和普通权限混在一起

### 产品上

5. 自动化功能只走自主分发，不上应用商店
6. 不把它声明为无障碍工具
7. 用户可以关掉自动化，关掉后手动配置仍可用

### 发布前

8. 把 `CaptureServer.java` 里"照抄 scrcpy"的注释改成"参考公开实现思路"
9. 补一份 `THIRD-PARTY-NOTICES`
10. **商业发布前找律师审阅一遍**

## 二、无障碍自动化：现在可以做了

### 2.1 之前那条禁令的来源

Google Play 政策的原话是：

> Accessibility API 不能用于：……**规避 Android 内置的平台安全控制机制**……
> Accessibility API 并非为实现下列用途而设计，应用也不得请求使用该 API 来实现这些用途：
> ……**能够自主发起、规划和执行操作或决策的应用**

**这条只对 Play 分发的应用有效。** GitHub 自主分发不在其约束范围内。

### 2.2 GitHub 自己的政策：我们有豁免

GitHub《可接受使用政策》第 5 节原文（英文，具效力）：

> We do not allow content or activity on GitHub that:
> **directly supports unlawful active attack or malware campaigns that are causing technical harms**
> — such as using our platform to deliver malicious executables or as attack infrastructure
> …… — **with no implicit or explicit dual-use purpose prior to the abuse occurring**; or
> uses our servers to disrupt or to attempt to disrupt, or to gain or to attempt to gain
> **unauthorized access** to, any service, device, data, account or network.

**两条都不适用于我们**：

| 政策要件 | 我们的情况 |
|---|---|
| "unlawful" 攻击或恶意软件活动 | 合法工具，用于用户自己的设备 |
| "with no dual-use purpose" | **我们明显有正当用途**（把手机音频送到蓝牙音箱），属于典型的双用途工具 |
| "unauthorized access" | **用户自己授权自己的设备**，不是未授权访问 |

而且 GitHub 上已经存在大量同类项目（AccessibilityService 自动化框架等）正常运行，
说明这类工具本身是被允许的。

### 2.3 但仍建议这样设计（降低被误判和被滥用的风险）

1. **无障碍功能默认关闭**，用户主动开启
2. **README 顶部写清楚**：这是什么、为什么需要这些权限、不收集任何数据
3. **代码透明**：无障碍服务只做哪几件事，写进注释和文档
4. **可随时关闭**，关掉后手动配置仍可用
5. 不要把它声明为 `isAccessibilityTool=true`

## 三、现在最要紧的事：开源合规

分发渠道变了，风险重心从"行政合规"转到了"**开源合规**"。

### 3.1 必须补的文件

| 文件 | 作用 | 现状 |
|---|---|---|
| `LICENSE` | MIT 协议全文 | **缺** |
| `THIRD-PARTY-NOTICES.md` | 第三方依赖的版权声明 | **缺** |
| `README.md` 权限说明段 | 为什么需要这些权限 | 部分有 |
| `SECURITY.md` | 安全模型与漏洞报告方式 | **缺** |
| `PRIVACY.md` | 明确"不收集任何数据" | **缺** |

### 3.2 第三方依赖清单（据 csproj 实测）

| 依赖 | 版本 | 许可 | 义务 |
|---|---|---|---|
| NAudio | 2.2.1 | MIT | 保留版权声明 |

| .NET 8 运行时 | — | MIT | 保留版权声明 |
| AndroidX / Material（手机端） | — | Apache-2.0 | 保留 NOTICE |

### 3.3 需要澄清的一处：scrcpy

`android/shell-server/src/com/nluemix/shell/CaptureServer.java` 的类注释里写着
「照抄 scrcpy 的采集方式」。**这句话需要改**，因为：

- scrcpy 是 **Apache-2.0**，如果被认定是衍生作品，必须保留版权声明和变更说明
- 但"用 shell 身份 + REMOTE_SUBMIX 采集系统音频"是**公开的技术事实**，不受著作权保护
- 从代码看，我们的协议、包头、发送逻辑都是自己写的

**建议改成**：「参考 scrcpy 公开的实现思路（shell 身份 + REMOTE_SUBMIX），代码为本项目独立实现」。
这样既诚实，也不会自认衍生。

### 3.4 弹窗在新场景下的定位

开屏弹窗**继续保留**，但它的性质变了：

- 之前：对抗应用商店和大规模用户的合规工具
- **现在：对使用者的信息披露 + 建立信任**

对开源项目来说，一个把所有权限和风险都摊开写的弹窗是**加分项** ——
它直接回答了"这东西是不是恶意软件"这个每个下载者都会问的问题。

内容可以稍微调一下语气，从"法律声明"变成"开发者跟你说实话"。
